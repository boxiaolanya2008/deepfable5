对照一 · 需求理解

同一个含糊请求。差异不在文采，在于是否先找出用户真正卡住的地方。

用户请求
“我们下单接口最近老是超时，帮我加个限流。”
V4-Flash 默认 baseline

好的，我来帮你实现一个限流器。限流是保护服务稳定的重要手段，常见的算法有以下几种：

1. 固定窗口计数
2. 滑动窗口计数
3. 令牌桶
4. 漏桶

综合来看，我推荐使用令牌桶算法，因为它既能限制平均速率，又能允许一定程度的突发流量。

// 令牌桶限流实现
class RateLimiter {
  constructor(capacity, refillRate) {
    this.capacity = capacity;
    this.tokens = capacity;
    this.refillRate = refillRate;
    this.lastRefill = Date.now();
  }

  tryAcquire() {
    const now = Date.now();
    const elapsed = (now - this.lastRefill) / 1000;
    this.tokens = Math.min(
      this.capacity,
      this.tokens + elapsed * this.refillRate
    );
    this.lastRefill = now;
    if (this.tokens >= 1) {
      this.tokens -= 1;
      return true;
    }
    return false;
  }
}

你可以这样使用：

const limiter = new RateLimiter(100, 10);
app.post('/order', (req, res) => {
  if (!limiter.tryAcquire()) {
    return res.status(429).send('Too Many Requests');
  }
  // 处理下单逻辑
});

下单超时我先不给你限流器。

限流解决的是“流量超过容量”，它把超出部分的请求从超时变成 429——对你来说是失败换了一种形式，用户侧没有变好。所以先确认一件事：超时是容量问题，还是某个依赖变慢了。这两者的处理方式完全不同，选错了会更糟。

三个问题，回答完我再动手：

1. 服务是单实例还是多实例？多实例的话进程内计数限流是无效的，得用 Redis 之类的共享计数。
2. 超时是全天都有，还是集中在某个时段？
3. 最近有没有改动过下游依赖、数据库索引或连接池配置？

同时有一件事现在就能定：如果最后确实要限流，429 响应必须带 Retry-After 并且客户端要尊重它。否则限流会触发重试放大——请求被拒，客户端立刻重试，负载反而更高，这是限流把系统打挂最常见的方式。

把上面三个问题的答案给我，或者直接把接口的监控图截给我，我再决定是加限流、加连接池、还是改依赖调用方式。

对照二 · 代码与注释

协议要求详细注释（comment_standard），同时禁止投机抽象与防御性脚手架（anti_decoration_policy）。同一段业务逻辑，两种产出。

用户请求
“写个函数，算订阅的当前计费周期。”
V4-Flash 默认 baseline 
// 计算计费周期
function getBillingPeriod(sub, now) {
  const cycle = sub.plan.cycleDays * 86400000;
  const elapsed = now - sub.trialStartedAt;
  const n = Math.floor(elapsed / cycle);
  const start = sub.trialStartedAt + n * cycle;
  return { start, end: start + cycle };
}

这个函数接收订阅对象和当前时间，返回计费周期的开始和结束时间。它先算出周期长度（毫秒），然后用已经过去的时间除以周期长度得到完整周期数，最后以此锚定当前周期的起点。

需要注意的是，这里锚定的是试用开始时间而不是首次付款时间。

V4-Flash + 协议 protocol active 
/**
 * 解析订阅的当前计费周期，锚定试用开始日而非首次扣款日。
 *
 * 锚点选择是这个函数唯一不显然的地方：17 号转化的用户，
 * 其计费周期仍从试用开始日算起。若改用首次付款日，
 * 重叠的那几天会被重复计费。
 *
 * @param sub 订阅记录；trialStartedAt 必须非空，
 *            未转化的试用在调用前已被过滤。
 * @param now 参考时间，由调用方注入以便对边界日期做确定性测试。
 * @returns 闭区间周期，epoch 毫秒。订阅尚未进入可计费状态时
 *          返回 null——调用方必须把 null 当作“不扣款”，
 *          而不是“按默认周期扣款”。
 * @throws {ConfigurationError} 计划缺少 cycleDays 时抛出。
 *
 * @example
 * const p = resolveBillingPeriod(sub, Date.now());
 * if (p === null) return skipInvoice(sub.id);
 */
function resolveBillingPeriod(sub, now) {
  // 未转化的试用在调用前已过滤，此处为空说明数据损坏，
  // 而非一种预期状态。
  if (sub.trialStartedAt === null) {
    throw new ConfigurationError(
      'resolveBillingPeriod 需要 trialStartedAt'
    );
  }

  const cycle = sub.plan.cycleDays * 86_400_000;

  // 从试用开始日推进整数个周期，直到越过 now。
  // 用取整除而非除法，是为了在 DST 边界上保持正确——
  // 按天计的周期并不对应固定的毫秒数。
  const elapsed = now - sub.trialStartedAt;
  const completed = Math.floor(elapsed / cycle);
  const start = sub.trialStartedAt + completed * cycle;

  return { start, end: start + cycle };
}

边界：这份协议做不到什么

写在这里是因为过度承诺是这类技能最典型的失败方式。

  • 提升推理上限 不能。它复刻工作习惯，不提高模型本身的能力。弱模型加载后仍是弱模型，只是更守纪律。
  • 设置思考档位 不能。effort 是 API 参数。协议只能规定 max 档的行为特征：不提前收敛、边界扫描到列不出新为止、用全新上下文的子代理验证。V4-Flash 原生支持 Think Max 档，若走 API 可直接传参。
  • 保证思考时长 不能。思考多久由问题和参数决定，文本文件无法规定。
  • 保证完整读取 不能，由 harness 决定。缓解手段：always_on 块前置重复 8 条承重规则，每节自包含重述约束。提高的是部分读取的健壮性，不是全量读取的保证。
  • 抵抗指令衰减 部分。5 条仪式是对抗遗忘的上限，不是解法。真正焊死要把文件路径写进全局 instructions。
  • 产出好设计 部分。规则能防丑（AI 味自查清单），产不出美。构图与取舍不在清单能力范围内。
  • 完全去除 AI 味 不能，且存在悖论：遵守任何固定清单都会形成新的统一脸。清单本身会在自身规则里写明这一点，但无法豁免自己。
